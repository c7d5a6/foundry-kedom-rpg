# Forge export formats

Four targets, one source. The pipeline they feed is described in
[../system/compendium-pipeline.md](../system/compendium-pipeline.md).

| Target | Consumer | Committed? |
|---|---|---|
| **YAML** | `packages/system/packs/_source/` → LevelDB → Foundry | yes |
| **JSON** | external tools, one-off scripts | no |
| **Markdown** | the Obsidian vault, for reading and printing | no |
| **Site JSON** | the public website's character generator | into the site repo |

The site target is designed but **not built**; see
[public-site-export.md](public-site-export.md).

## Rules that apply to all four

**One direction only.** SQLite → files. Nothing reads files back into SQLite. The alternative
creates two sources of truth for one record, and reconciling them means either building a diff
UI or inventing conflict rules
([ADR-011](../research/05-decisions.md#adr-011--sqlite-is-the-content-source-of-truth-yaml-is-the-reviewable-artefact)).

**Deterministic output.** Same database, same bytes. Keys sorted, indentation fixed, UTF-8 with
LF endings, no timestamps anywhere in the output. Without this every export produces a diff
full of noise and the reviewability that justifies the YAML stage disappears.

**Identity never regenerated.** `slug` and `foundry_id` are read from the database, never
computed at export time. A regenerated Foundry `_id` breaks every reference to that document
in every existing world.

**Generated-file header.** Every exported file opens with a comment saying it is generated and
must not be hand-edited.

**UTF-8 correctness.** Kedom place names carry diacritics from a constructed language —
`Kedôm`, `Nitól`, `Ñiziel`. No escaping, no normalisation, no transliteration on the way out.

## YAML — compendium sources

The one that matters. Written into `packages/system/packs/_source/<pack>/`, one file per
document, compiled to LevelDB by `pnpm packs:build`.

The shape is a Foundry document, because that is what the CLI expects:

```yaml
# GENERATED by Kedom Forge. DO NOT EDIT -- edit in Forge and re-export.
_id: kQ7mXp2vR9tL4nHs
name: Survive
type: skill
img: systems/kedom/assets/skills/survive.webp
system:
  slug: survive
  attribute: wis
  description: <p>...</p>
  specializationMode: parameterized
  specializations:
    - slug: survive.environment.forest
      label: Forest
      parameter: environment
    - slug: survive.tracking
      label: Tracking
_key: '!items!kQ7mXp2vR9tL4nHs'
```

Notes on the decisions visible here:

- **`_id` comes from `foundry_id`**, stable across exports.
- **`_key`** is the LevelDB key the CLI requires; it is derived, not stored.
- **`system.slug`** is duplicated into the system data even though it is also the filename
  stem, because the Foundry-side code reads it from `system`, and a filename is not data.
- **`specializations` is denormalised into the document.** The schema stores them as rows
  ([schema.md](schema.md#specialization)), but the Foundry data model holds them as a sub-array
  on the skill ([../system/data-model.md](../system/data-model.md#the-shape)). This is the one
  place the two shapes deliberately differ: relational for authoring, embedded for play.

One file per document rather than one file per pack, following dnd5e's 4,871 sources and
shadowdark's per-document JSON. Per-document files mean a content change touches one file, so
the diff says what actually changed.

Filenames are the slug: `survive.yml`, `conduct.yml`. Predictable and collision-free, since
slugs are unique.

### Pack mapping

| Pack | Rows |
|---|---|
| `skills` | `skill` with its `specialization` rows |
| `origins` | `race`, `background`, `class` as `origin` items with a `subType` |
| `conditions` | hand-authored, not from Forge |
| `injuries` | hand-authored, not from Forge |
| `journals` | region and race descriptive text |

`race_grant`, `skill_choice`, and `skill_choice_option` do not get packs of their own — they
export as nested arrays on the owning document, matching the `grants` and `choices` shape in
[../system/data-model.md](../system/data-model.md#references-between-documents).

## JSON — interchange

The same document structures, emitted as one JSON file per pack rather than per document.
Gitignored.

This exists for external tooling and one-off scripts. It is explicitly **not** an import
format and not a backup — `dump.sql` is the backup.

## Markdown — back to the vault

Human-readable output for reading, printing, and cross-checking against the original notes:

```
exports/markdown/
  skills.md              one table, all skills and specialisations
  races/<slug>.md         one page per race with its grants
  backgrounds/<slug>.md
  regions/<slug>.md       races, prevalence, and their backgrounds
```

The region page is the useful one, because it renders the whole authoring graph in one place —
which is the fastest way to notice that a race has no backgrounds or a background offers a
choice with only one option.

Front matter carries the slug so the vault can link by identity rather than filename.

Gitignored: the vault is upstream brainstorming and these are a read-only view of downstream
state. Writing them into the repo would blur which direction content flows.

## Site JSON — the public character generator

**Designed, not built.** Static JSON committed into the public site repo
(`/home/c7d5a6/projects/rpg/kedom/`), fetched by a Vue character generator on GitHub Pages.

Split into small index files that carry only what a picker renders, plus one detail file per
entity carrying the prose. The site fetches an index on load and a detail file on each
selection, so a reader who never opens the generator downloads none of it.

The full design, the measured payload, and what the existing WWN generator reveals about this
schema are in [public-site-export.md](public-site-export.md).

## `dump.sql` — the reviewable database

Not an export target in the same sense; it is how a binary file becomes reviewable.

```sh
pnpm forge:dump     # -> packages/content/dump.sql
```

Committed alongside `content.sqlite`. Rows ordered by primary key so the diff is stable, and
schema statements first so a reviewer sees structural changes before data changes.

This is the direct answer to mothership, which commits binary LevelDB packs and therefore
cannot diff its own content at all.

## Validation before export

Export refuses to run on invalid content rather than emitting something Foundry will choke on.
The checks:

- every `slug` matches the slug pattern and is unique
- every `foundry_id` is a valid 16-character Foundry ID and unique
- every foreign key resolves (belt and braces — the database enforces this, but the export is
  the last chance to catch a bug in a migration)
- every `skill_choice.pick_count` is at least 1 and no greater than its option count
- every `race_grant` has the column matching its `kind` populated
- no `specialization` belongs to a skill whose `specialization_mode` is `none`
- no `race` grants a skill that does not exist — which would have caught
  [Q10](../rules/99-open-questions.md#q10--racial-skill-grants-name-skills-that-do-not-exist) at
  authoring time instead of at play time

Failures list every problem at once. Fixing content one error per run is miserable.
